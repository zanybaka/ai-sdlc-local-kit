# ai-task-product — pipeline reference

Moved byte-faithfully from `SKILL.md`. Normative; load on demand.

## Post-decompose pipeline (mandatory after sdlc-backlog-decompose)

Run these steps in order on every new or refreshed backlog before handoff:

### 1. Priority pass

Set `Priority:` P0–P3 per playbook (see contract doc). For each P0/P1 task, add to Task Context:

`Risk: P1, approved YYYY-MM-DD` or a PRD section reference. Product records approval; user only for irreversible business risk.

| Level | Use for |
|-------|---------|
| P0 | Production, security, breaking contract |
| P1 | Critical path for the feature |
| P2 | Normal work (default) |
| P3 | Polish, optional cleanup |

### 2. Verify pass

Set `Verify:` per stack (`python-full`, `node-full`, `web-e2e`, `*-quick`, `none`) from policy (`.ai-task/docs/ai-task-verify.md`). Omit line only when `default_profile` is correct for every task in the repo.

For tasks touching **state initialisation, data loading, or module entry points**, DoD must include: "tested with empty/null/no-data input" — see `docs/stability-testing.md` for the principle and stack anti-patterns.

### 3. Depends on inference

Read TECHSPEC and phase structure. Write **technical** dependencies:

- Predecessor in the same phase (foundation before consumer).
- Contract/schema task before implementation that uses it.
- Shared library before dependents.
- Not a dependency: a shared file with the `AUTO-GENERATED by <generator>` header that both tasks only regenerate - see the decomposition rules in `SKILL.md`.

Use comma-separated ids. Leave empty only when the task is truly independent. Load **sdlc-contract-guard** when deps cross public APIs.

File order alone is not sufficient for `ai-task plan`.

### 4. Agent pass

- Default **`Agent: auto`** for all implementation tasks.
- **`Agent: human`** only for coordination-only work (merge handoff, committee prep) with no `ai-task run`.
- Do not set `claude`/`cursor`/`codex`/`devin` without a written reason in Task Context.

### 5. Next slice (wave 1 hint)

Name **1–3 task ids** suggested for the **first teamlead wave** (`plan --batch N`): eligible together (no deps within the slice), aligned with P0/P1 on the critical path. **Teamlead** re-plans each later wave from live `BACKLOG.md` after review/verdict and your backlog edits; do not treat this slice as a frozen plan for the whole run.

### 6. Task id format pass

Before handoff, confirm every task-shaped checkbox line uses **`PREFIX-123`** (digit-only suffix, title on the same line). See `.ai-task/docs/ai-task-backlog-contract.md`.

When `.ai-task/` exists:

```bash
ai-task dor --json
ai-task plan --auto-batch --json   # ids from the next slice must appear here
```

Fix any `field: Task id` / `action: fix_task_id_format` gaps (rename ids and update `Depends on:` references). Do not rely on `dor` metadata checks alone: invalid ids are invisible to `plan` until this pass passes.

## Validator-conformance metadata fix (fast path)

**Mechanical, validator-named gaps no longer round-trip through product:** teamlead fixes them inline — Size bucket normalization (`XS`→`S` when scope is plainly small), `fix_task_id_format` renames, dead `Depends on:` id removal — with one mandatory `decision log --phase cross --choice mechanical_metadata_fix` row (task id + field + old→new), then reruns `dor`. Expect such rows in the journal; audit them at retro.

Product handoff remains for **judgment calls** — fix the field and return quickly, no PRD or TECHSPEC round-trip:

| Gap | Product action |
|-----|----------------|
| Right S/M/L bucket unclear from scope, or the task is really XL+ | Set `Size:` from task scope; split instead of inflating to `L` |
| `Verify:` profile semantics (which profile matches the DoD) | Align to policy; split an E2E child if needed |
| Priority change, scope mismatch, split/defer | Edit the block, split, or defer with rationale |
| Dependency that should exist but does not | Add the dep or the missing task |

Log `decision log --phase cross --choice product_response` when `.ai-task` exists. Teamlead reruns `dor` or `plan --strict`.

**Worked example:** `Size: XS` on four small bug tasks is validator-named and mechanical: teamlead sets `Size: S` inline (scope is a small skill/doc edit) and logs `mechanical_metadata_fix`; delivery continues without a product round-trip. Had the right bucket been unclear (scope possibly XL+), teamlead would log `delivery_feedback` and product would size or split.

## Sibling tasks: author a class-guard into the DoD

When a bug/task is a **sibling / regression / "root cause" of** an already-fixed bug, its Task DOD must require a **class-guard** (a lint rule, a shared primitive, or a sync-test against the source-of-truth), not only the local fix — otherwise the class keeps recurring (in one delivery phase ~7–8 of 8 bugs were siblings while `rework_rate` stayed ~0, because each fix patched an instance). Add a DoD line like *"the change also prevents the **class** (guard X), not just this instance"* and prefer a `Verify:` that exercises the guard. Teamlead enforces this at verdict (see *Sibling tasks must close the class*); authoring it into the DoD up front is cheaper than catching it in review.

## Shared-contract changes: imprint the rebuild invariant into the DoD

When a task changes a **shared contract** whose rebuild invariant lives OUTSIDE the task (a new label, an n8n node, an endpoint, an env var, a wire format), author the matching cross-cutting rebuild invariant straight into the Task DOD. Verify only checks that one task's own DoD, so an invariant that stays implicit is silently dropped: a new `bug` label once never reached the onboarding label set, and the operator-checklist owner-steps snapshot went stale, because neither was in any DoD.

The contract classes, their rebuild docs, and the exact DoD line to add are named in one place: `docs/ai-task-backlog-contract.md` (Shared-contract rebuild invariants). Example DoD line: *"new `bug` label -> add it to the onboarding label set in `<doc>`"*. `ai-task dor` also surfaces this as an advisory note (`rebuild_invariant_reminders` in `dor --json`) for open tasks whose block signals a contract change but never names the rebuild doc; treat the note as a DoR fix you own, not a user escalation. If the invariant genuinely does not apply, mark it not-applicable in the block so the note stays quiet. Authoring it up front is cheaper than the verify note catching it in review.

## Prioritization playbook

1. Read open tasks and metadata (not file order alone).
2. Propose **next slice** (1–3 ids) with rationale.
3. On reprioritize: edit `Priority:` and `Depends on:`; note blocked tasks and review gates.
4. **Defer**: `- [~]` + reason in Task Context.
5. **Split**: partial parent DoD + child tasks via **sdlc-backlog-add**.
